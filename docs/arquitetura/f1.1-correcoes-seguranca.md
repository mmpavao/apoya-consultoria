## ACHADO 1 — 🔴 CRÍTICO: autorização falsificável em `tarefa_mover_etapa` — CORRIGIDO

**Problema original:** `ator` e `ator_tipo` vinham do payload da chamada. Um agente podia
passar `ator_tipo: "humano"` para burlar `requer_aprovacao` e auto-aprovar etapas.

**Correção implementada (db.js + tarefas.js):**
- `validateApiKey` retorna `ator_tipo` derivado da chave (`is_human_delegate ? "humano" : "agente"`)
- `tarefa_mover_etapa` usa `identity.ator_tipo` — payload `ator_tipo` é IGNORADO
- `identity` passado como terceiro argumento para TODOS os handlers (index.js)
- `isAdmin` removido — substituído por `identity.escopo_setores.includes("*")` + `is_human_delegate`

**Caminho para aprovação humana via MCP:**
- Única opção: chave `mcp_api_keys` com `is_human_delegate = true`
- Uso previsto: webhook do painel web (sessão humana autenticada gera token → webhook chama MCP)
- Agentes com chave normal NUNCA podem avançar etapas `requer_aprovacao`, independente do payload

## F1.1b — ACHADO CRÍTICO NOVO: RLS permissiva em `mcp_api_keys` — CORRIGIDO

**Identificado por:** Claude Code (validador), 11/06/2026 — auditoria read-only no Supabase
**Migration:** 009_rls_mcp_api_keys.sql

**Problema:** 3 policies com `roles={authenticated}` ativas simultaneamente com a
`service_role_only_mcp_keys`. Qualquer usuário logado (`authenticated`) conseguia:
- SELECT: ler `key_hash`, `scopes`, `escopo_setores` de todas as chaves
- UPDATE: alterar campos — ex: `escopo_setores=['*']`, `is_active=true`, `is_human_delegate=true`
- INSERT: criar novas chaves

Isso anulava completamente o controle de escopo por setor implementado em F1.1 (Achado 2).

**Correção (migration 009):**
```sql
DROP POLICY IF EXISTS authenticated_read_mcp_keys   ON public.mcp_api_keys;
DROP POLICY IF EXISTS authenticated_update_mcp_keys ON public.mcp_api_keys;
DROP POLICY IF EXISTS authenticated_insert_mcp_keys ON public.mcp_api_keys;
```

**Policy remanescente (correta):**
```
service_role_only_mcp_keys [ALL] roles={public} qual=(auth.role() = 'service_role')
```

**Confirmação pós-migration:** service_role SELECT retornou rows corretamente (worker não quebrou).

**Critérios de aceite:**
1. Usuário `authenticated` não-admin recebe negação em SELECT de `mcp_api_keys` via REST (RLS block)
2. Usuário `authenticated` não-admin recebe negação em UPDATE
3. service_role (worker) continua fazendo SELECT com sucesso — `validateApiKey` intacto
